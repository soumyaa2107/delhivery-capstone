# Delay Intelligence — Delhivery regional operations analytics (synthetic data)

One connected repository that answers three questions for the regional operations head:
**how long will a parcel take** (Part B), **which parcels will miss their promise** (Part C) and
**which hubs need which playbook** (Part D). Part A cleans the data that all later parts use.
All data is synthetic, produced by `generate_data.py`; no real Delhivery records are used.
Money is in Indian Rupees (INR).

## How to run

From a fresh clone, in this order:

```bash
pip install -r requirements.txt
python generate_data.py          # prints: 24 1224 48
python part_a_clean_eda.py       # data/modelling_table.csv + outputs/part_a_*.csv
python part_b_regression.py
python part_c_classification.py
python part_d_segments.py
python package_model.py          # regenerates models/*
python predict_delay.py          # outputs/new_shipment_actions.csv
```

`models/delay_model.pkl` is regenerated by running `python package_model.py`. The committed pickle loads
reliably only on the scikit-learn version pinned in `requirements.txt` (1.8.0); if your installed versions
differ, re-run `package_model.py` instead of loading the committed file. `src/shipment_prep.py` holds the
shared constants and the `clean_shipments` / `build_features` functions used by every script, including
`predict_delay.py`, so training and scoring use identical preprocessing.

## Data findings

Source: `outputs/part_a_checks.csv`, `part_a_delay_by_group.csv`, `part_a_correlations.csv`. The raw export has 1,224 rows;
24 exact duplicates were removed, leaving 1,200 parcels, of which 278 are delayed (delay rate 0.2317).

1. **Express is delayed most often.** Express has a delay rate of 0.4897 (119 of 243 parcels), against 0.2056 for Standard and 0.0857 for Economy.
2. **Delay climbs steeply with hub tier.** Tier 1 hubs: 0.0400, Tier 2: 0.2150, Tier 3: 0.4400 (176 of 400 parcels).
3. **Delay climbs even more steeply with distance.** 0.0219 for 0-200 km, 0.1368 for 201-400 km, 0.4364 for 401-600 km and 0.8523 for 601+ km.
4. **Strongest correlations with `delivery_hours`:** `promised_hours` (0.8372), `distance_km` (0.4013) and `n_stops` (0.3247). `hub_daily_capacity` is a close fourth in absolute terms (-0.3237).
5. **Why `declared_value_inr` was log-transformed.** The (median-filled) column is right-skewed — mean INR 1,533.05 versus median INR 1,121.50 — while after the log the mean (7.0277) and median (7.0224) nearly coincide, so the transformed column is roughly symmetric.

## Model results (regression)

Source: `outputs/part_b_*.csv`. Split 840 / 180 / 180; the scaler was fitted on training rows only (training-row column means are 0.0, test-row maximum absolute mean is 0.2187, proving no leakage).

- **Baseline.** Predicting the training mean gives validation R² = -0.0212 (RMSE 18.86 h): it explains none of the variation, so any useful model must clear this bar.
- **Winner on validation.** Linear regression, validation RMSE 4.89 h (R² 0.9313), narrowly ahead of gradient boosting (4.92 h, R² 0.9306), random forest (5.51 h) and the decision tree (6.28 h). Its single test evaluation gives RMSE 4.52 h and R² 0.9493.
- **Tree depth.** Depths 1-3 are high-bias: train and validation errors are both high (depth 1: 11.63 / 12.13 h). Deep trees are high-variance: depth 12 has train RMSE 1.36 h but validation 7.35 h, and with no limit train RMSE is 0.00 h against 7.84 h on validation, a gap of 7.84 h. Depth 6 has the lowest validation RMSE (6.28 h) and is used for the tree candidate.
- **Learning rate.** Validation R² is 0.7127 at 0.01, 0.9306 at 0.1 and 0.8440 at 1.0. At 0.01 each of the 100 trees corrects too little, so the ensemble is still under-fitted (too slow); at 1.0 each tree takes a full-size step and the ensemble overshoots and over-fits the training noise. 0.1 balances the two.
- **Cross-validation disagrees with the validation ranking.** On the 1,020 train+validation rows (shared `KFold(5, shuffle=True, random_state=42)`), gradient boosting scores mean R² 0.9353 (std 0.0045) versus 0.9261 (std 0.0048) for linear regression. The validation gap (4.89 vs 4.92 h) is tiny and measured on 180 rows, whereas the five-fold figure averages many more held-out parcels. I would therefore **ship gradient boosting**: the data contain non-linear effects (a sale-window penalty that only hits Express, and a rain effect that only applies on long lanes) that a linear model cannot represent. The rule-based "final model" scored once on test is linear regression, as the brief specifies, and it did well (R² 0.9493); the two models are close and either is defensible.

## Model results (classification)

Source: `outputs/part_c_*.csv`. Stratified split 840 / 180 / 180 with 195 / 42 / 41 delayed parcels.

- **Blind baseline.** Predicting "never delayed" scores accuracy 0.7667 on validation but catches 0 of 42 delayed parcels (recall 0.0). It looks decent only because 77% of parcels are on time — it is useless for the task.
- **Models at the 0.5 rule (validation F1).** Logistic regression 0.8046, decision tree (depth 6) 0.7470, default random forest 0.7848; all three have accuracy 0.8833-0.9056.
- **Noise columns.** The five bookkeeping columns carry a combined 0.2245 of the 17-column forest's importance, although they have no signal: a forest splits on them to fit noise. By F-score they rank 8, 12, 14, 16 and 17 with F-scores between 0.0230 and 4.5847, so all five fall outside the top 7; the lowest F-score in the top seven is 36.7281. Importance spread over noise is a warning against trusting raw forest importances on small data.
- **Choosing k.** Validation F1 for k = 5, 7, 10, 12, 17 is 0.6988, 0.8333, 0.7857, 0.8049, 0.7848. k = 5 drops real signal (the rain and sale-event flags rank 6th and 7th), while k = 7 keeps exactly the seven genuine signal columns and scores best; k = 7 is used.
- **Tuning.** Grid search (135 fits; best CV accuracy 0.8952) reached validation F1 0.7750 and randomized search (45 fits; 0.8905) reached 0.7848, while the **untuned forest on the same 7 columns scored 0.8333** and was chosen. Tuning did not beat the default on validation, which says that differences of a few F1 points on a 180-row validation set (42 delayed parcels) are mostly noise: one parcel moves F1 by roughly 0.01-0.02. Cross-validated accuracy on training rows was the more reliable signal, and the three candidates are practically equivalent.
- **Threshold.** The rule is the highest threshold with validation recall ≥ 0.80. Recall is 0.8333 at 0.5 (precision 0.7955, F1 0.8140) and drops to 0.7619 at 0.6 (precision 0.8889), so **the threshold is 0.5**. Lower thresholds buy recall at the cost of precision: at 0.3 recall is 0.9286 but precision falls to 0.6964, and at 0.1 recall 0.9762 with precision only 0.4824.
- **Final test (threshold 0.5, evaluated once).** Precision 0.6889, recall 0.7561, F1 0.7209 (TN 125, FP 14, FN 10, TP 31). Test recall is lower than validation recall (0.8333); with only 41 delayed parcels one parcel is about 2.4 recall points, so the 7.7-point gap is roughly three parcels and is plausibly sampling noise, but it also shows the recall≥0.80 target is not guaranteed on new data.

## Operations recommendation

- **Escalate segment (9 hubs, mean delay rate 0.4600):** Nagpur (HUB13, 0.46), Kochi (HUB15, 0.36), Patna (HUB17, 0.46), Ranchi (HUB18, 0.38), Guwahati (HUB19, 0.62), Raipur (HUB20, 0.48), Bhubaneswar (HUB21, 0.40), Siliguri (HUB23, 0.44) and Agartala (HUB24, 0.54). The Standard segment has 7 hubs (delay rate 0.0257) and Watch has 8 (0.1550).
- **Tier labels that mislead (`tier_vs_segment_mismatch.csv`):**
  - HUB07 Kolkata is labelled Tier 1 but behaves like Watch (delay rate 0.14).
  - HUB13 Nagpur and HUB15 Kochi are labelled Tier 2 but behave like Escalate hubs (0.46 and 0.36).
  - HUB22 Dehradun is labelled Tier 3 but behaves like Watch (0.20).

  The tier label should therefore be treated as a starting guess, not a playbook; use the data-driven segment (refreshed regularly) to assign the playbook.
- **Alert threshold 0.5.** On the test rows, 6.9 of every 10 flagged parcels are really delayed (precision 0.6889) and 7.6 of every 10 delayed parcels are caught (recall 0.7561).
- **New parcels.** Of the 48 new parcels, 8 were flagged: 6 need escalation to the hub manager and 2 need a proactive customer call (`outputs/new_shipment_actions.csv`).
- **Why K = 3 is kept.** The across/within ratio keeps rising (2.8940 for K=2, 5.3928 for K=3, 6.3047 for K=4, 6.8866 for K=5), but K = 4 has cluster sizes 8-7-5-4 and K = 5 has 8-7-4-3-2: both contain clusters of fewer than 6 hubs, too small to carry their own playbook. Operations runs exactly three playbooks, and K = 3 gives sizes 9-8-7 with a large jump from K = 2.

## Production plan

**(a) Production-readiness mapping**

| Characteristic | Repository item |
|---|---|
| Accuracy | Held-out validation and test metrics in `part_b_metrics.csv`, `part_c_final_test.csv`; threshold chosen from the recall rule |
| Reliability | `clean_shipments` handles duplicates, casing, gaps and the 999 kg sentinel; `predict_delay.py` fails loudly on a missing file instead of guessing |
| Reproducibility | Fixed `random_state`s, pinned `requirements.txt`, deterministic scripts, byte-identical repeated runs of `predict_delay.py` |
| Performance (speed) | Scoring 48 parcels is a single `predict_proba` call on a 100-tree forest with 7 selected columns |
| Maintainability | Shared `src/shipment_prep.py`; model, threshold, feature order and medians stored as separate small files in `models/` |
| Consistency | The same `clean_shipments` / `build_features` and the stored medians are used for training and scoring |
| Monitorability | The outputs in `new_shipment_actions.csv` (probability, flag, action) can be logged weekly and compared to outcomes |

**(b) Quantities to monitor, with numeric triggers**

- Weekly delayed share of delivered parcels: baseline 0.2317; investigate if it moves outside 0.18-0.29 for two consecutive weeks (outside the sale window).
- Weekly share of parcels flagged: on the test rows the share is about 0.25 (45 of 180); investigate if it moves outside 0.18-0.32.
- Recall on parcels whose outcome is now known: test recall was 0.7561; trigger a retrain if it falls below 0.65 over a month with at least 40 delayed parcels.
- Share of missing `distance_km` or `parcel_weight_kg` values: 3% in the training export; investigate above 8%.

**(c) Retraining and the sale window.** Retrain monthly, and sooner if any trigger above fires, re-estimating medians, the threshold and the hub segments each time. The 15-28 September sale window should be compared with the same kind of event (last sale window, using `sale_event_flag`), not with ordinary weeks: it adds hours (and 12 extra hours for Express), so higher delay in that window is expected and is not drift. Data drift here would look like a shift in the distribution of distance, stops or service mix; hubs migrating between segments; or relationships changing (for example the rain effect no longer depending on lane length).

## Limitations

1. **Synthetic data.** Everything is generated from known formulas, so results are cleaner than real logistics data and the model has never faced real-world noise, regional events or label errors.
2. **Few delayed parcels in the test set.** Only 41 delayed parcels were available, so test precision and recall are noisy: one parcel shifts recall by about 2.4 points.
3. **Threshold tuned on one validation split.** The threshold of 0.5 and the choice among the three tuned candidates both rest on a 180-row validation set with 42 delayed parcels and may not be stable on another split.
4. **Hub segments use only 24 hubs and 50 parcels each.** K-Means on 24 points is sensitive to the seed and hub order for K = 4 and 5; the segments describe the past quarter, not necessarily the future.
5. **The cost of errors is not quantified.** The brief says a miss costs more than an unnecessary call, but no INR figures exist, so the recall target of 0.80 is a rule of thumb rather than a cost-optimal choice.
